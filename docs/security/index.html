Section 23

Security

What the tool does:

  • No database port is open to the internet.
  • SSH uses keys only, on a port other than 22. With --tailscale, public SSH is closed.
  • Every new node is hardened at boot. See Node hardening.
  • All passwords are random (48 hexadecimal characters).
  • Postgres uses scram-sha-256 passwords.
  • Each project role can connect only to its own database.
  • Backups are encrypted.
  • Commands that go to a node travel on SSH standard input, so passwords do not show in process lists.
  • The state file (pgha.db) has mode 0600. SQLite gives its -wal and -shm files the same mode.
  • The web console listens on 127.0.0.1 by default. Its API needs a token, uses an HttpOnly, SameSite=Strict cookie, blocks cross-origin writes, and checks the Host header.

#The SSH check

The console and most commands reach the nodes with ssh in batch mode, so nothing can ask for a passphrase. Before a new cluster is created, pgha up and the console test this host. They stop before anything is created when:

  • ssh, ssh-keygen or ssh-add is missing.

  • No private key here matches the public key for the new nodes. pgha reads the keys ssh would use: your SSH config, --ssh-identity, the default files and the SSH agent. With --ssh-key-name, it compares the key stored at Hetzner.

  • The matching key has a passphrase and is not in an SSH agent.

  • The key file permissions are too open, so ssh ignores the file.

  • With --tailscale, this host has no tailnet address. pgha cannot tell which tailnet the address belongs to.

  • --ssh-allow has no IPv4 range, or this host has no IPv4 route. pgha reaches the nodes on their IPv4 address.

  • --ssh-allow leaves out the public address of this host. Only for a narrow range, pgha reads that address from checkip.amazonaws.com. If the lookup fails, you get a warning.

These tests connect to nothing, so the create ends with real proof: pgha connects to every node over SSH, for up to 8 minutes. That finds what no test can see in advance, like tailnet ACLs, a blocked port 22, a single-use Tailscale auth key or a custom image.

If a node does not answer, the task fails and pgha deletes the resources of this run, including empty volumes, unless you chose to keep them. It never deletes a cluster that existed before, or an adopted server.

An old host key for a new node's address is removed from known_hosts first, because Hetzner reuses addresses.

#A custom SSH port

New clusters do not use port 22. sshd listens on 22022, unless you set another port with --ssh-port or SSH port on the new cluster form. The firewall opens that port and not 22, and pgha stores it as the pgha-ssh-port server label, so later commands find it from any computer. Your network must allow outbound connections to that port.

--ssh-port 22 keeps the old port. Clusters made before this default have no label and stay on 22; pgha never moves a live cluster.

  • The port is fixed for the life of the cluster. pgha up refuses a change, because the firewall and the running sshd would no longer match.
  • The ports 2379, 2380, 5432, 6379, 6432, 8008, 8009, 8010 and 26379 are refused. The nodes use them.
  • It works with Tailscale: sshd moves on the tailnet too.
  • pgha adopt does not support it yet.
  • Connect with ssh -p <port> root@<address>.

#Skipping the check

--skip-ssh-check and Create anyway skip only the tests before the create, for example for a hardware key pgha cannot test. The connection at the end always runs. Adding nodes to an existing cluster runs the same steps.

#Node hardening

These run first in the boot script of every new node, or before its services start. Nodes made before this release are not changed. Adopted servers are not changed either.

LayerWhat pgha sets
sshdKeys only. Root logs in with a key, because pgha connects as root. No password or keyboard login, no agent, TCP or X11 forwarding, no tunnels. 30 second login grace.
Host firewallnftables drops by default. Open: the SSH port, ICMP, and DHCP replies. etcd (2379, 2380) only from the other nodes. Postgres, PgBouncer and Patroni (5432, 6432, 8008) only from the private network, the same range as pg_hba. With PgBouncer: its health check (8010) only from the private network. With Redis: Redis, Sentinel and the role check (6379, 26379, 8009) only from the private network. With Redis TLS: 6390 only from the private network, where the load balancer reaches it. With Tailscale, SSH only on tailscale0.
Metadata serviceOnly root can reach 169.254.169.254. It serves the boot data, which holds every password of the node.
Kernelsysctl settings in /etc/sysctl.d/90-pgha-hardening.conf: no redirects or source routing, SYN cookies, restricted dmesg, kernel pointers, BPF and ptrace. rp_filter is loose, because strict mode breaks private routes and Tailscale.
Updatesunattended-upgrades installs security updates. It never reboots, and it skips Patroni, etcd, Postgres, PgBouncer, pgBackRest, Redis and Python, because a restart of Patroni or etcd causes a failover and a PgBouncer restart drops every client. needrestart never restarts those services after a library update such as libc or OpenSSL. Apply those updates and reboots yourself, one node at a time, replicas first.
SecretsThe boot copy of the Patroni config is deleted. So are the staged Redis files in /etc/pgha/redis. Redis and Sentinel need the password; the role check reads it from a file only the redis user can read.

The cloud firewall does not cover the private network, which is why the host firewall matters most with --network, where other servers share it.

Two things are left out on purpose, because they can lock pgha out:

  • fail2ban. Password guessing cannot work with keys only, but a computer that offers a wrong agent key first could be banned while pgha polls it.
  • MaxAuthTries below the default. The same computer would fail every login. Use --ssh-identity to offer one key.

SSH port forwarding is off on the nodes, so ssh -L to a node does not work. Connect through the load balancer, or run psql on the node.

#Client TLS

--tls sets how clients connect to Postgres. You choose it when the cluster is made. Redis has its own switch, --redis-tls (section 16).

ModePostgresPgBouncerClients
requiredssl = on. pg_hba uses hostssl, so plain network logins fail.client_tls_sslmode = requireMust use TLS.
optional (default)ssl = on. pg_hba uses host.client_tls_sslmode = allowChoose. libpq tries TLS first (sslmode=prefer).
offssl = offNo TLSPlain only.
  • up makes a CA for the cluster (ECDSA P-256, 20 years) and stores it in the state file. It signs one server certificate for each node (10 years). The names are the node name, its private address, localhost and 127.0.0.1.
  • The load balancer passes TLS through. Its address is not in the certificates, so use sslmode=verify-ca with pgha ca-cert, not verify-full.
  • Replication between nodes uses TLS too when TLS is on. With required, plain replication logins fail.
  • Connections on 127.0.0.1 and the Unix socket stay allowed without TLS. PgBouncer, backups and the db commands use them.
  • A cluster keeps its mode. A later up with no --tls uses the live mode, and up refuses a different one. Clusters made before TLS support are off.
  • Certificates are not renewed. The node certificates expire after 10 years.

What you must know:

  • etcd and the Patroni API have no TLS. They use plain connections on the private network. The host firewall limits who can reach them.
  • Do not use --public-lb for production data unless --tls is required.
  • The default --ssh-allow range is open to all addresses. Set your own range, or use --tailscale.
  • The server user data contains the cluster passwords. A root user on a node can read it. This is the same trust level as the node itself.
  • The state file contains all passwords in plain text. Protect it.
  • With alerts on, the webhook URL is in the state file, in cloud-init user data for a new node, and in /etc/pgha/webhook.curl (mode 0600). The check script does not contain the URL.
  • The web console has no TLS. With --listen 0.0.0.0, the token and the connection strings cross the network in plain text. Use an SSH tunnel or a TLS proxy. Run the console on a server shows both. Anyone with the token can delete clusters, and can read and change all data through the SQL editor.
  • etcd has no authentication. All servers on the private network can reach it. Do not put servers you do not trust on this network. That includes every server already on a network you pass to --network.
