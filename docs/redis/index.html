Section 16

Redis

pgha runs Redis with Sentinel on the same kind of nodes, either alone on a new cluster or next to Postgres on a cluster that runs. It reuses the network, firewall, SSH key and port, Tailscale, host hardening, the load balancer, the state store and down.

./pgha redis up --name cache                 # new Redis-only cluster, 3 nodes
./pgha up --name app --redis                 # new cluster with Postgres and Redis
./pgha redis add --name pgha                 # add Redis to a live Postgres cluster
./pgha redis status --name cache             # password, URLs, Sentinels

#How it works

Every node runs Redis 8 (redis-server and redis-sentinel) from the Redis apt repository, packages.redis.io. Ubuntu 24.04 ships 7.0, so pgha pins the Redis packages above Ubuntu's. A node that already runs Redis keeps its version: an upgrade restarts Redis, which waits for a planned window. One node is the primary and the others replicate from it. Each node also runs pgha-redis-health, a small Python service on port 8009 that answers the load balancer with the node's role. It asks Redis on the node's private address, where the load balancer sends clients, so a Redis that does not listen there takes no clients. systemd restarts Redis, Sentinel and the check when they stop, and retries until the private address is up at boot. Clusters made before this release get the new check when you run pgha redis add again: it keeps the Redis config and data.

#Redis TLS

Turn it on with --redis-tls on pgha up --redis, pgha redis up or pgha redis add, or with Redis over TLS on New cluster and Encrypt with TLS on the Redis page. A public load balancer needs it: without TLS, pgha refuses Redis on a public load balancer, because the password would cross the internet in clear text.

./pgha redis up --name cache --public-lb --redis-tls
./pgha redis add --name shuttlers-cloud --redis-tls   # a live cluster with a public load balancer
./pgha ca-cert --name cache > cache-ca.crt
redis-cli --tls --cacert cache-ca.crt -u 'rediss://:<password>@<load balancer>:6379/0'
  • Each node serves TLS on port 6390 with the same password. The load balancer sends 6379 and 6380 there, so every client through it uses TLS. Port 6379 on each node stays plain for replication and Sentinel, and the host firewall opens it to the private network only.
  • The cluster CA signs a certificate for each node. It names the node and both load balancer addresses, so a client can check the address it connects to. pgha ca-cert prints the CA. A cluster without Postgres TLS gets a CA when Redis TLS turns on.
  • pgha turns TLS on live with CONFIG SET, then CONFIG REWRITE: no restart, no failover. On a new cluster it runs once the load balancer exists, so its addresses go in the certificates.
  • TLS stays on. pgha never sends a Redis port back to plain Redis.
  • pgha redis status prints rediss:// URLs, and the public ones when the load balancer has a public address.
  • A client must trust the cluster CA, or it fails with certificate signed by unknown authority. The .env tab on the Redis page gives REDIS_CA_CERT next to REDIS_URL, in quotes so dotenv readers keep the line breaks. Load it as a root CA, for example RootCAs in Go.

When the primary stops answering for 5 seconds, the Sentinels agree (quorum: a majority of the nodes) and promote a replica. The load balancer follows within about 10 seconds. A Sentinel-aware client follows at once. The old primary comes back as a replica.

pgha redis add installs on the primary first and waits until every Sentinel sees every replica and every other Sentinel before it opens the load balancer ports. Without that wait, a failover in the first seconds can pick a leader that knows no replica, and it aborts.

#Change the eviction policy or the memory cap

./pgha redis config --name cache                                   # show them
./pgha redis config --name cache --redis-policy allkeys-lru       # cache: drop old keys at the cap
./pgha redis config --name cache --redis-memory-pct 60

The change goes to every node with CONFIG SET, so Redis applies it at once: no restart, no failover, no dropped clients. CONFIG REWRITE then writes it to /etc/redis/redis.conf, so it outlives a restart and a Sentinel failover. The values are also saved in the state store, so nodes that up adds or replaces later boot with them, and a flag left out of redis up, up --redis or redis add keeps the saved value. The cap is 10-90% alone and 10-50% next to Postgres. If a node does not answer, the command names it and fails; run it again when the node is back. In the console, open the cluster, choose Redis, and use Eviction and memory.

redis up makes 20 GB volumes by default: they hold the append-only file and snapshots, and the data set lives in memory. Choose the server type for memory.

#Add Redis to a live cluster

./pgha redis add --name pgha --redis-policy allkeys-lru

This runs over SSH on every node. Postgres keeps running. The command installs the packages, writes the configuration, adds a rule for ports 6379, 26379 and 8009 from the private network to the host firewall, starts the services, waits for Sentinel, adds ports 6379 and 6380 to the load balancer, and labels the servers. It is safe to run again: a node that has Redis keeps its configuration, because Sentinel rewrites it after a failover.

An lb11 holds 5 ports. A PgBouncer cluster uses 4, so Redis does not fit. --lb-type lb21 lets the command change the load balancer type, which costs more. The command checks this first: without room, it stops before it changes any node. In the console, open the cluster and choose Redis.

redis add refuses a cluster with a public load balancer, an adopted server, or a node without an address.

#Clients

./pgha redis status --name cache
# Read-write: redis://:<password>@10.0.1.x:6379/0
# Read-only:  redis://:<password>@10.0.1.x:6380/0

With a Sentinel client, give it the Sentinel addresses, the master name and the password for both Redis and Sentinel. In redis-py:

from redis.sentinel import Sentinel
s = Sentinel([("10.0.1.11", 26379), ("10.0.1.12", 26379)], password=PW, sentinel_kwargs={"password": PW})
primary = s.master_for("cache", password=PW)

#Grow and remove

pgha up or pgha redis up with more locations adds nodes. New nodes replicate from the live primary. A plain pgha up on a Redis-only cluster keeps it Redis-only, and on a cluster with Redis it adds Redis to new nodes. Existing Sentinels keep their quorum. pgha down deletes a Redis cluster like any other.

#Redis limits

  • Redis TLS covers clients through the load balancer. Sentinel (26379) and replication stay plain on the private network.
  • One password for every client: there are no per-app Redis users yet.
  • A Redis-only cluster has no backups, PgBouncer or databases. The console hides those pages, and the CLI and API refuse those commands. Alerts work: pgha redis up --monitor, pgha monitor install, or the Alerts tab on the Monitoring page (section 20).
  • The load balancer uptime of the Redis ports comes from its health checks; there is no client check through them yet.
  • Replication is asynchronous. A failover can lose about a second of writes.
  • This is Sentinel, not Redis Cluster: one primary holds all the data. Scale up the server type for more memory.
  • Updates of redis-* wait for a planned window, like Postgres. Redis 8 is under the AGPLv3, RSALv2 or SSPLv1, as you choose.
