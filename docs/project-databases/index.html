Section 14

Project databases

Each project gets its own database and its own login.

./pgha db create shop_api
# Database ready: shop_api
# Read-write: postgresql://shop_api:<password>@10.0.1.x:5432/shop_api
# Read-only:  postgresql://shop_api:<password>@10.0.1.x:5433/shop_api

What db create does:

  1. Creates the login role shop_api with a random password.
  2. Creates the database shop_api. The role owns it.
  3. Removes access for all other roles (REVOKE ALL ... FROM PUBLIC).
  4. Stores the password in the state file.

Rules:

  • A second db create for the same name keeps the same password.
  • Port 5432 goes to the leader. Port 5433 goes to the replicas.
  • Replicas can be a short time behind the leader. Do not read your own writes from port 5433.
  • The connection string uses the private load balancer address. Your applications must be on the same Hetzner private network.
  • --public uses the public address. This needs up --public-lb. Use a cluster with --tls required for this, or set sslmode=require in the client. With --tls off, data on a public address is not encrypted.
  • With --tls required, the connection strings end in ?sslmode=require.
  • db list shows PASSWORD for a database that this tool did not create.

The db commands use SSH to the leader and run psql as the postgres operating system user.

#Extensions

Most extensions need a superuser for CREATE EXTENSION, and project logins are not superusers. pgha ext add does it for them.

./pgha ext add timescaledb hll --database shop_api
./pgha ext list

Most packages come from apt.postgresql.org (PGDG). Two come from a pinned source: read Pinned sources. Each one exists for PostgreSQL 14 to 18 on amd64 and arm64.

<v> is the Postgres major version. Any other extension whose files are on every node, like the contrib extension citext, also works.

What ext add does:

  1. Asks every node for its extension files, its preload list and its role. It stops if a node does not answer.
  2. Installs the missing packages on each node with apt-get. For a pinned entry it adds the source first.
  3. Saves the extensions in the state file. New nodes install them at boot.
  4. If an extension needs a library, adds it to shared_preload_libraries in the Patroni config with patronictl edit-config, with the settings of the extension that the config does not have yet. It keeps the libraries in use, also those of an adopted server. Then it waits until every node has the new value.
  5. Restarts Postgres with patronictl restart, one node at a time: the replicas first, the primary last. It waits for each replica to stream again. Patroni keeps the leader lock, so there is no failover. Writes pause for a few seconds (about 2 in the Docker test), and PgBouncer clients in a transaction get an error.
  6. Runs CREATE EXTENSION IF NOT EXISTS ... CASCADE on the primary, in each --database, or in the default database.

Rules:

  • A missing preload library stops Postgres. That is why the packages go on every node before the preload change, and why new nodes get the list.
  • --no-restart stops after step 4. The console and ext list show "Restart pending". Run ext add again, or choose Restart now in the console.
  • On a new cluster, up --extensions and the console create form install the packages at boot. The console also adds them to the default database.
  • pg_cron runs jobs only on the primary. Schedule jobs for other databases with cron.schedule_in_database.
  • ext remove drops the extension. It stops when objects use it. The package and the preload list stay.
  • Unattended upgrades skip packages that start with postgresql. Update extension packages in a planned window, then run ALTER EXTENSION ... UPDATE.
  • pg_duckdb and timescaledb (either build) cannot share a database. Both define public.time_bucket. Put them in different databases. A new cluster takes one or the other.
  • timescaledb and timescaledb-tsl are two builds of one extension. ext add timescaledb-tsl on a cluster with the Apache build removes the Apache package, installs the TSL build and restarts every node. It does this only when no database has the extension. With data in hypertables, dump the data first.
  • docs/analytics-extensions.md in the repository compares the analytics extensions that are not in the catalog, like Citus columnar.

In the console, open a cluster and choose Extensions. Pick a database, then Add or Remove. An add that needs a restart asks first. On New cluster, an extension that cannot join the ones you picked is grey.

#Pinned sources

PGDG does not ship pg_duckdb or the TimescaleDB build with compression. pgha takes them from one apt source each, pinned in three ways:

EntrySourceKey fingerprintVersion
pg_duckdbhttps://repo.pigsty.io/apt/pgsql/noble (Pigsty)9592A7BC7A682E7333376E09E7935D8DB9BD8B201.2.0-1PGSTY~noble for PostgreSQL 14 to 18
timescaledb-tslhttps://packagecloud.io/timescale/timescaledb/ubuntu/ (Timescale)1005FB68604CE9B8F6879CF759F18EDF47F244172.31.0 for 16 to 18, 2.28.3 for 15, 2.19.3 for 14
  1. The key. pgha downloads the signing key and checks that it holds one key with the fingerprint above. If not, it stops. apt checks the repository with that key only (signed-by).
  2. The packages. A file in /etc/apt/preferences.d gives every package from that host priority -1, so apt never installs or upgrades one.
  3. The version. The same file gives the pinned version of the catalog packages priority 1001. apt-get upgrade does not move them.

The files are /etc/apt/keyrings/pgha-<source>.asc, /etc/apt/sources.list.d/pgha-<source>.list and /etc/apt/preferences.d/pgha-<source>. A new version comes with a new pgha release. The pins fit Ubuntu 24.04 (noble) only, so these entries need the ubuntu-24.04 image.

Things to know:

  • Pigsty is a third-party project. One person builds and signs its packages. pg_duckdb 1.2.0 is the only version Pigsty has for Ubuntu 24.04, and upstream marks 1.2.0 experimental. Test it before you use it in production.
  • The Timescale License allows the TSL build in your own products. It does not allow you to sell TimescaleDB as a database service to others.
  • The TSL packages need the newest Postgres minor version, for example postgresql-17 (>= 17.11). apt installs it from PGDG with them. The restart that follows starts the new minor version.

pg_duckdb settings, set in the Patroni config with the extension:

SettingValueWhy
duckdb.postgres_rolepgha_duckdbWithout it, only superusers can use DuckDB. pgha grants this role to the owner of each database that gets pg_duckdb.
duckdb.max_memorya quarter of the server memory, in MBThe default is 4 GB per connection. Past the cap, DuckDB writes to temporary files.

pgha does not change a setting that the Patroni config already has. To change the cap, on a node:

patronictl -c /etc/patroni/config.yml edit-config -p duckdb.max_memory=2048

Use DuckDB with SET duckdb.force_execution = true, or with a DuckDB function like read_parquet. It works on the replicas too, so heavy reports can use port 5433. With PgBouncer, add duckdb.force_execution to track_extra_parameters in /etc/pgbouncer/pgbouncer.ini if clients set it per session.
