#8.3 pgha estimate

Shows the estimated monthly bill. It creates nothing. It reads live prices from the Hetzner API, so it needs the token.

#8.4 pgha up

Creates the cluster.

  1. It shows the bill.
  2. It asks for confirmation. --yes skips the question.
  3. It creates the SSH key, network, firewall, volumes, servers and load balancer. --network skips network creation and uses that network.
  4. It writes the state file.

You can run up again. It skips the resources that exist. It does not change resources that exist.

If a step fails after retries, up deletes the resources that this run created, newest first, and then stops with the error. It never deletes:

  • resources that existed before this run, for example the nodes of a cluster that you grow, or a run that completes an earlier one;
  • a network you gave with --network;
  • an adopted server. adopt removes the labels it added and detaches the server from a network it attached.

The cleanup also runs after Ctrl+C. It has 15 minutes. If a delete fails, the error names it and says to run pgha down. --keep-on-failure keeps the new resources, for example to look at a failed server.

The load balancer joins the private network before up adds the nodes as targets. A run that completes an earlier one attaches an existing load balancer that has no network.

--monitor installs the alert timer on nodes created in this run. Read section 18. If a node already exists, up still succeeds and prints:

monitor installs on new nodes; run pgha monitor install

The servers install the software after up returns. This takes about 5 minutes. Use pgha status to see when the roles show primary and replica.

#8.5 pgha adopt

Builds the cluster around an existing server. Read section 19.

FlagMeaning
--serverName of the existing Hetzner Cloud server. Required.
--extra-packagesExtension packages to install on the new nodes.
--monitorInstall the alert timer. Read section 18.
--keep-on-failureKeep this run's new resources when creation fails.
--yesSkip the confirmation.

adopt rejects the backup flags, --pgbouncer and --tls optional or required. An adopted cluster uses plain connections.

#8.6 pgha status

Shows each node with its location, server status, role, addresses, SSH host and volume size. It also shows the load balancer addresses and the TLS mode.

The role comes from the load balancer health checks:

RoleMeaning
primaryThe node is the leader.
replicaThe node is a healthy replica.
startingNo health check is green yet.

#8.7 pgha down

Deletes the load balancer, servers, firewall, network and the SSH key that the tool created. A network passed with --network is not deleted.

FlagMeaning
--delete-volumesAlso delete the data volumes. All data is lost.
--delete-backupsAlso delete this cluster's pgBackRest backups and WAL archives. The bucket stays. A node must be reachable.
--yesSkip the confirmation.

Without --delete-volumes, the volumes stay and continue to cost money. Without --delete-backups, object storage files stay and continue to cost money.

down is blocked when the cluster has an adopted server.

#Sign-in

With --auth firebase or --auth supabase, the console shows a sign-in form. The browser signs in with the provider, and the console checks the token on the server:

  • Firebase: the ID token signature, issuer, audience and expiry, with Google's public keys.
  • Supabase: Supabase Auth answers GET /auth/v1/user for the token. This also checks that the session was not signed out.

Then the console sets its own session cookie for --session-ttl. The cookie key is new at each start, so a restart ends all sessions. A browser that is still signed in with the provider gets a new session without the form.

--auth-allow takes a comma separated list:

EntryAllows
ops@example.comOne email address.
@example.comEvery address at that domain (not subdomains).
*Any user of the Firebase or Supabase project.
anything elseOne provider user ID (Firebase uid, Supabase user id).

Emails count only when the provider says they are verified. Users are made and removed in the Firebase or Supabase dashboard; the console has no sign-up. If public sign-up is on in the project, do not use *.

Set up the provider:

  • Firebase: turn on the sign-in methods in Authentication, and add the console's domain to the authorized domains. localhost is there by default. OAuth sign-in opens a pop-up.
  • Supabase: turn on the providers in Authentication. For OAuth, add the console URL (for example https://pgha.example.com/) to the redirect URLs.

Scripts can call the API with Authorization: Bearer <token>: the console token, a Firebase ID token, or a Supabase access token. The access list applies.

The console logs each sign-in and each change (POST, PATCH, DELETE) with the user's email.

The global flags --token, --state-dir, --db, --mode and --ssh-identity apply too. --name has no effect; the console lists all clusters.

Health is healthy when there is one primary and all nodes are running and in the load balancer, degraded with one primary and fewer healthy nodes, and unavailable with no primary.

Create, delete, import, backup and alert tasks run in the background, one at a time per cluster. Their time limits are the same as the CLI. When you stop the console with Ctrl+C, it waits for the running tasks.

The task history goes into the operations table, so it stays after a restart. The log is saved every 2 seconds while a task runs. A task that was running when the console died shows as failed at the next start.

#Monitoring

The Performance tab reads every node over SSH every 10 seconds while the page is open. It needs no agent on the nodes: the console sends a short Python script that reads /proc, the local Postgres and the local Patroni API. Sampling stops 3 minutes after the last viewer leaves. The console keeps one hour in memory; a restart clears it.

GroupCharts
PostgresTransactions, connections, active queries, cache hit ratio, rows read and written, WAL rate, replication lag, longest transaction, lock waits, rollbacks, temp files, database size
HostCPU, I/O wait, load, memory, data disk, disk reads and writes, network in and out

Each node also gets a card with its role, Patroni state and timeline, connections, memory, disk and uptime. The primary's pg_stat_replication shows how far each replica is behind.

The Activity tab lists client sessions on the primary or on one node, with lock waits. Cancel stops the running query. End disconnects the session.

#Database explorer

Open a database from the Databases page, or use SQL editor.

  • Row edits find the row by its primary key. Tables without a primary key, views and foreign tables are read-only here.
  • Values travel as Postgres text and are bound as parameters. NULL and an empty string are different. On insert, columns left on DEFAULT get their default.
  • The SQL editor runs in a read-only transaction until you tick Allow writes. It runs as the postgres superuser and commits on success. It shows the last statement's result, up to 1000 rows. The timeout is 30 seconds, up to 10 minutes.
  • Writes go to the primary. Reads can also run on a replica.
  • SQL and values reach the node base64 encoded, never as shell text.

The nodes need python3 and python3-psycopg2. up and adopt install them.

The JSON API is under /api/. Each call needs the session cookie or Authorization: Bearer <token>. Requests that change data must come from the same origin. A delete needs ?confirm=<name>. A cluster delete also takes volumes=true and backups=true.

#8.12 pgha ca-cert

Prints the cluster CA certificate. Clients use it to check the server:

./pgha ca-cert --name pgha > ca.crt
psql "host=10.0.1.x dbname=shop_api user=shop_api sslmode=verify-ca sslrootcert=ca.crt"

It fails for a cluster with --tls off.
